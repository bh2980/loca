# 입력 타입: 노드는 코어 + 타입별 확장 (설계, 2026-10-20)

상태: 승인, 구현됨 (2026-10-20). 이전 설계(워크플로 `subject` + 곳곳의 거르기·거절, 그 뒤의 "대상 없음 + 실행 때 고르기")를 대신한다. 아직 실제로 돌린 프로젝트가 없으므로 이전 형식은 옮기지 않는다(마이그레이션 없음, 기본 워크플로는 새로 만든다).

## 문제
대사와 용어는 항목의 생김새가 다르다. 대사는 화자·청자·장면·앞뒤 대사·번역 후보가 있고, 용어는 원문·표기·메모·쓰인 횟수·용례가 있다. 그래서 문맥, 저장 노드, 조건이 읽는 값, 묶음 방식이 타입에 따라 달라진다. 지금까지는 이 차이를 다루는 규칙이 흩어져 있었다(검증 오류, 묶음 목록 거르기, 노드 목록 거르기, 실행 창 목록 거르기, 런타임 예외).

## 원칙
1. **입력 타입은 한 곳에서 선언한다.** 워크플로의 진입 노드가 "이 워크플로에는 무엇이 들어오는가"(`input: 'lines' | 'terms'`)를 정한다. 함수의 매개변수 타입과 같다.
2. **노드는 코어 + 타입별 확장이다.** 노드는 범용이고, 입력 타입에 맞는 확장 칸만 붙는다. 다른 타입의 확장 값은 저장돼 있어도 쓰이지 않는다.
3. **타입별 차이는 한 표(`INPUT_TYPES`)에만 있다.** 화면, 검증, 실행기, CLI, 채팅 도구가 모두 이 표를 읽는다. 노드·화면마다 `if (terms)`를 두지 않는다.

## INPUT_TYPES (packages/shared)
| | lines (대사) | terms (용어) |
|---|---|---|
| 항목 이름 | 대사 · 줄 | 용어 · 개 |
| 실행 창 · 대상 목록 | 장면·묶음 트리 | 상태별 용어 목록 |
| 실행 창 · 필터 | 프로젝트 상태, 대사 태그·자동 태그 | 후보·확정·버림, 용어 자동 태그 |
| AI 묶음 | 코어(개수별·하나씩) + 장면별·대본 전체 | 코어만 |
| AI 문맥 | 코어 + 앞 대사(번역)·이전 장면·청자·말투 | 코어 + 용례 n줄 |
| 조건 행 | 코어 + 상태·종류·태그·자동 태그·청자 | 코어 + 용어 상태·표기 유무·쓰인 횟수 |
| 이 타입에만 있는 노드 | 번역 후보 기록, 청자 설정, 상태 변경, 형식·용어 검사, 태그 붙이기 | 용어 표기 저장, 용어 상태 변경 |
| 프리셋 | 번역·검수·수정·다듬기·청자 추정·추출·작품 분석 … | 용어 번역 |

코어(어느 타입이든): AI 노드의 모델·지시문·출력·동시 처리 수·제한 시간·입력(앞 단계 결과)·문맥(용어집·인물 명단·프로필·관계·문서·확정 자료만·상한), 조건의 노드 결과·방문 횟수·실패 종류·번역문, 모으기, 스크립트, HTTP, 실패로 끝내기, 반영 노드 중 양쪽에 쓰이는 것(용어 저장·인물·관계·말투 규칙·사건·문서).

## 저장 형식
- 진입: `{ input }` 하나. 어떤 항목을 넣을지는 실행 범위(`statusIds`·`marks`·`tagIds`·`groupIds`·`unitIds`·`termIds`, 입력에 맞게 해석)만 정한다.
- AI 노드: 필드는 지금처럼 한 층(`context`, `batch.mode`)에 두고, 어느 칸이 어느 입력의 확장인지는 `INPUT_TYPES`가 정한다(`contextFields`, `batchModes`). 편집기 버튼(설정 › 에디터)도 같은 `context`를 쓰므로 저장 형식을 둘로 나누지 않았다. 다른 입력의 칸 값은 남아 있어도 쓰이지 않는다.
- 함수: `FUNCTIONS[fn].inputs`(옛 `subjects`)가 어느 입력의 노드인지 정한다. 프리셋은 `input`(기본 lines).
- 실행: `runs.subject`는 그 워크플로의 `input`(실행 시점에 고정).

## 화면
- **진입 노드:** "입력: 대사 / 용어" 하나뿐.
- **노드 설정:** 코어 칸 + 입력 타입의 확장 칸. 설명에 "(용어일 때)" 같은 단서가 없다.
- **노드 목록(팔레트):** 코어 노드 + 입력 타입에 있는 노드·프리셋만. 다른 타입 노드가 이미 놓여 있으면(타입을 바꾼 경우) 노드에 오류로 보인다. 이것은 설계 오류라 실행 전에 막는다(같은 표 한 곳에서 판단).
- **실행 창:** 하나의 틀(대상 목록, 필터 상태·태그, 준비 상태, 예상, 모델)에 내용만 입력에 따라 바뀐다. 목록은 입력별로 묶어 모든 워크플로를 보인다. 연 화면에서 고른 것(장면, 대사, 용어)은 같은 입력이면 범위의 시작값이다. 필터는 워크플로마다 마지막 값을 브라우저에 기억한다.
- **CLI·채팅:** `--term`·`termIds`는 용어 워크플로의 범위, 장면·대사 옵션은 대사 워크플로의 범위. 타입은 워크플로가 정하므로 `--terms`·`subject`는 없앤다.

## 실행기
- 항목의 종류는 실행의 `subject`. 노드 확장은 그 타입 것만 읽는다(코드 경로가 표를 따른다).
- 다른 타입 노드에 닿는 일은 검증이 막으므로 런타임 `unsupported`는 안전망으로만 남긴다.

## 하지 않는 것
- 한 실행에 대사와 용어를 섞지 않는다.
- 노드마다 입력 타입을 따로 정하지 않는다(워크플로 하나에 하나).

## 바뀌는 곳 (구현 순서)
1. shared: `INPUT_TYPES`, 진입 `input`, AI 확장 필드, 함수 `inputs`, 검증(표 한 곳), 프리셋 `input`, 기본 워크플로.
2. server: 실행 생성·preflight·runner·조건 데이터·plan/start(채팅·CLI)가 워크플로 `input`을 따름, `scope.subject` 제거.
3. web: 진입 노드, AI·조건·함수 설정의 확장 칸, 팔레트, 실행 창.
4. CLI·skills·spec·reference, 테스트.
