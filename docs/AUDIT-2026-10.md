# loca 전체 감사 (2026-10-10)

**목적**: 이 시스템이 수만 줄 규모의 실제 게임을 안정적으로 분석하고 번역할 수 있는지 확인한다.
**기준**: 커밋 `b2e7184`(HEAD). 기존 설계가 옳다고 전제하지 않았다.
**방법**:
- 정적 추적: 영역 6개(엔진, AI 실행 계층, 작품 지식, 가져오기·저장·그래프, 채팅·도구·SSE, 검증 체계)
- 목 LLM 규모 실측: HEAD를 격리된 작업 트리와 데이터 폴더에서 실행. 9천 줄(합성 7,969줄)과 5만 줄(합성 48,734줄)
- 기존 기록: 스모크 DB의 Orwell 실행 기록, CLI 로컬 세션 기록(`~/.grok/sessions`, agy 로그)

실제 유료 모델과 CLI 호출은 하지 않았다.

## 표기
- **[확인]**: 재현했거나 코드·기록으로 직접 확인함
- **[실측 필요]**: 근거는 있으나 수치나 발생 여부를 아직 재지 못함
- **[제안]**: 결함은 아니지만 바꾸는 편이 나은 것
- **추정**: 실측을 규모에 맞춰 늘린 값. 실측과 구분한다.
- 위치는 HEAD 기준 `파일:줄`이다.

## 1. 결론

**지금 구조로는 수만 줄 게임을 안정적으로 처리할 수 없다.** 문제는 기능 몇 개의 성능이 아니라 다섯 가지 근본 원인에서 나온다.

| # | 근본 원인 | 대표 증상 |
|---|---|---|
| R1 | **규모·비용이 계약에 없다.** 테스트·목 LLM·샘플·수용 기준 어디에도 호출 수, 토큰, 시간 기준이 없다 | 오늘 Orwell 실제 실행에서 300만 토큰 이상을 쓴 뒤에야 낭비를 발견했다. 42개 테스트는 모두 통과하고 있었다 |
| R2 | **실행 엔진이 "지금 대기 중인 줄"을 즉석에서 잘게 묶는다.** 실행 계획이 없고, 매 tick마다 대기열 전체를 다시 읽는다 | 요청당 평균 1.3~6줄. 장면 순서는 UUID 순(사실상 무작위). 5만 줄이면 서버가 다운되고 재시작해도 다시 죽는다 |
| R3 | **AI 실행 계층이 CLI를 상태 없는 함수처럼 다룬다.** 요청마다 프로세스와 작업 폴더를 새로 만들고, CLI가 붙이는 것을 통제하지 않는다 | Grok은 요청마다 우리 프롬프트의 약 8배를 덧붙인다. 토큰은 실제보다 약 40% 적게 기록된다 |
| R4 | **작품 지식의 책임이 겹치고 검증이 없다.** 작품 분석, 자료 갱신, 청자 추정, 용어 추출이 같은 원문을 따로 읽고, AI 결과를 근거 확인 없이 자동 확정한다 | 틀린 말투 규칙(Symes→Player 하십시오체)이 자동 확정되어 번역 27줄 중 23줄을 틀리게 만들었다 |
| R5 | **변경 알림과 화면 갱신에 양 조절이 없다.** 이벤트를 합치지 않고, 큰 응답을 통째로 다시 받는다 | 1,551줄 실행에 변경 이벤트 100개. 실행 상세를 열어 두면 알림마다 수 MB를 다시 받는다 |

반대로 다음은 규모에서도 문제가 없었다.
- 가져오기 검증과 트랜잭션
- 키 유일성
- 목록·필터·FTS 응답(4.9만 줄에서 5~77ms)
- 체인형 그래프의 레이아웃(5.5만 노드 8초)
- 배치 변경의 rev 충돌 검사

## 3. 확인된 문제

심각도는 **치명**(실행 불가·데이터 손실), **높음**(비용·정확성에 큰 영향), **중간**, **낮음**이다. 우선순위는 4장 로드맵의 단계 번호다.

### 3.1 치명

#### C1. 3만 2,767줄 이상 실행하면 서버가 죽고, 재시작해도 계속 죽는다 [확인]
- **위치**: `apps/server/src/engine/runner.ts:212`(`settle`의 `inArray`), `:262`(`batches`), `:450`(`selectRunUnits`), `:59`(`setInterval(() => void this.tick())`). `main.ts`에 `unhandledRejection` 처리가 없다.
- **조건**: 한 노드에 대기 줄이 32,766개를 넘을 때. 범위 없이 "전체 번역"을 하면 4만 줄 프로젝트도 해당한다.
- **증거**: 4만 8,734줄 목 실행에서 첫 tick에 프로세스가 종료됐다. 재기동하면 DB의 `running` 실행 때문에 즉시 다시 종료됐다.
- **같은 원인 계열**: `script-query.ts:287` `exportLines`(`loca export --all`이 3.3만 줄 이상에서 500 오류), `routes/source.ts:149` `PATCH /units`.
- **근본 원인**: 항목 수에 비례하는 `IN (…)`을 청크 없이 쓴다. 실행 하나의 오류를 실행 단위로 격리하지 않고, 프로세스 수준 방어도 없다.
- **개선**
  - 대기열 조회를 `run_items JOIN units`로 바꾸거나, 꼭 필요한 곳만 청크(≤5,000)로 나눈다.
  - tick 안에서 실행별로 try/catch를 걸고, 오류가 난 실행은 일시정지하고 이유를 기록한다.
  - 프로세스 수준 핸들러를 둔다.
- **효과**: 5만 줄 실행이 가능해진다.
- **위험·검증**: 변경 위험이 낮은 기계적 수정이다. 5만 줄 목 실행과 export 회귀 테스트로 검증한다.
- **우선순위**: 0단계

#### C2. 레이아웃 계산 중 프로젝트를 지우면 서버가 죽는다 [확인]
- **위치**: `routes/projects.ts:42`(`void computeLayouts`), `services/layout.ts:74-88`
- **재현**: 가져오기 직후 100ms 뒤에 삭제하면 `FOREIGN KEY constraint failed`가 unhandled rejection으로 터진다.
- **개선**: 최상위에서 예외를 처리하고, 삭제 시 워커를 종료한다. 레이아웃 계산은 프로젝트별로 직렬화한다.
- **우선순위**: 0단계

#### C3. AI 결과가 사람이 고친 번역을 조용히 덮어쓴다 [확인, 코드]
- **위치**: `engine/functions/index.ts:90-103`(`setStatus`의 `applyCandidate`), `routes/source.ts:212-238`(`PATCH /units/:id`는 rev 검사 없음)
- **조건**: 실행 중인 줄을 사람이 고치거나 채팅 제안을 수락한 뒤, 러너가 그 줄의 적용 노드에 도달할 때
- **영향**: 대표 번역이 AI 후보로 바뀐다. 사람 번역은 후보 이력에 남지만, 사용자는 바뀐 걸 알 수 없다.
- **추가 문제**: 같은 범위를 두 번 실행해도 막지 않는다(비용 2배, 나중에 끝난 쪽이 덮어씀).
- **개선**: 항목 생성 시 줄의 `updatedAt`을 기록하고, 적용할 때 바뀌었으면 후보로만 남기고 검토로 보낸다. 활성 실행에 이미 있는 줄은 빼거나 경고한다.
- **우선순위**: 2단계

### 3.2 높음: 비용과 처리량

#### H1. 요청이 너무 작다: 장면 경계, 하류 노드 쪼개짐, 무작위 순서 [확인]
- **위치**: `runner.ts:260-273`(`batches`: 장면 경계에서 끊고, `groupId` UUID로 정렬), `:196-205`(하류 노드는 지금 도착한 줄만으로 묶음)
- **증거**: 2.2절 표. 설정 크기 30~120인데 실제 요청당 1.3~5.9줄이었다. 자료 갱신의 장면 처리 순서는 `120 221 290 382 99999 142 225 60…`였다.
- **영향**
  - 호출 수가 5~20배 늘어난다. CLI에서는 호출마다 고정 비용이 붙으므로 그대로 비용이 된다.
  - 자료 갱신의 "순서대로 쌓기"와 앞 장면 번역 문맥이 무작위가 된다.
- **근본 원인**: 실행 계획 없이 tick마다 즉석에서 묶는다.
- **개선**
  - **실행 계획 단계**: 실행 생성 시 대본 순서로 연속 장면을 토큰 예산까지 묶는다.
  - **노드별 모으기**: 크기가 찼거나, 상류에 이 노드로 올 줄이 없거나, 일정 시간이 지났을 때 보낸다.
- **효과**: 호출 수 1/5 이하를 목표로 한다(DESIGN 6.1 수용 기준).
- **위험·검증**: 묶음이 커지면 누락 위험이 커진다(H5와 함께 해결). 9천 줄 현실형 샘플로 노드별 호출 수와 평균 줄 수를 단언하는 테스트로 검증한다.
- **비고**: 미완성 변경(작업 트리)은 연속 장면 묶음과 정렬만 다룬다. 하류 쪼개짐과 `inArray`는 그대로다.
- **우선순위**: 2단계

#### H2. CLI가 요청마다 우리 프롬프트의 수 배를 덧붙인다 [확인: Grok·agy / 실측 필요: Claude·Codex·opencode]
- **위치**: `packages/ai/src/cli.ts:28-71`(args), `:157`(호출마다 `mkdtemp`), `:164`(`cwd`)
- **Grok**
  - `--tools ''`만 쓴다. 스킬 주입(`~/.grok/skills`, `~/.agents/skills`, Claude 호환 스캔), 사용자 규칙, `~/.claude` 훅 11개가 그대로 켜져 있다.
  - 작업 폴더가 호출마다 달라져서 그 뒤쪽은 캐시되지 않는다. 시스템 프롬프트를 바꿔도 합계가 그대로였던 이유다(바뀐 부분은 전체의 약 7%).
  - 끌 수 있는 수단: 환경변수 `GROK_CLAUDE_SKILLS_ENABLED=0` 등, 큐레이트된 `--agent`, 고정 작업 폴더. 근거는 `~/.grok/docs/user-guide/26-config-reference.md:117-132`이다.
- **agy**
  - 시스템 프롬프트 교체나 도구 끄기 옵션이 없다.
  - `--json-schema`가 강제 호출을 추가로 일으킨다(149건).
  - 2회째 모델 요청의 정체는 미확인이다.
- **Codex**: 기본으로 켜진 기능이 많다(apps, browser_use, plugins, skill_search…). 우리는 hooks, shell, multi_agent만 끈다. 실제 고정 토큰은 미측정이다.
- **Claude Code**: `--safe-mode`는 CLAUDE.md, 스킬, MCP, 훅을 끄지만 기본 시스템 프롬프트는 그대로다. 실제 고정 토큰은 미측정이다.
- **추론 강도**: 프로필에 effort가 비어 있으면 CLI 기본값이 쓰인다(Grok은 `high`). 출력 토큰의 대부분이 추론 토큰이다.
- **개선**: 5장의 CLI별 요인 실측 후 어댑터에 적용한다. 모델 호출 없이 먼저 할 수 있는 확인이 있다(`grok inspect --json`으로 스킬·훅 0개 확인, `codex features list`).
- **효과**: 요청당 고정 토큰이 줄고 캐시 적중이 가능해진다. 크기는 실측이 필요하다.
- **우선순위**: 4단계(실측 승인 후)

#### H3. 토큰과 비용 기록이 실제보다 적다 [확인]
- **위치**: `cli.ts:86-93`(`usageOf`), `:127`(opencode `{}`), `openai.ts:41`, `pi.ts:87`, `runner.ts:339-361`(System One `{}`), `:380-381`(실패·취소 호출은 사용량 미기록)
- **버리는 값**
  - Grok·Claude: 캐시 입력, 비용
  - Codex: 캐시 비율, 추론
  - agy: `cache_read_tokens`
  - opencode, System One: 전부
  - 모든 연결: 실패하거나 재시도한 호출의 토큰
  - 채팅: 사용량을 저장하지 않음
- **증거**: Grok 87건 기준 기록 127만, 실제 약 219만(**약 42% 과소**). Grok 문서의 usage 필드와 세션 기록으로 확인했다.
- **근본 원인**: 사용량 형식을 연결마다 따로 읽고, 실패 경로는 기록하지 않는다.
- **개선**: 연결 공통 정규화(전체 입력·캐시 입력·추론·출력·보고된 비용), 시도 단위 기록, 채팅 사용량 저장.

감사 직전에 시작한 ①(측정)·②(묶음·누락 재요청) 변경이 커밋되지 않은 상태로 있다.

- 연속 장면 묶음

- 실행 기록 칼럼

이 변경은 H1(일부), H3(일부), H5(일부)를 다루지만 **C1의 `inArray`, 하류 노드 쪼개짐, 실패 경로 사용량은 다루지 않는다.** 테스트 2개도 깨뜨린다. 그대로 쓰지 않고, 로드맵 0·2단계에서 이 감사 결과에 맞춰 다시 짠다.

## 8. 진행 기록

### 0단계 (2026-10-12) 완료
- C1: 줄 수에 비례하는 id 목록은 나눠 보낸다(`db/chunk.ts`). 실행기는 대기열 전체를 data와 함께 읽지 않고, instant 노드는 tick당 2,000줄까지만 처리한다. 한 실행의 오류는 그 실행만 멈춘다. 프로세스 수준 처리기를 둔다. 3만 4천 줄 실행 테스트와 5만 줄 목 실행으로 확인했다.
- C2: 레이아웃은 예외를 내지 않고, 프로젝트별로 하나씩 실행하며, 삭제 시 취소하고, 5분 타임아웃이 있다.
- H3: 모든 연결의 사용량을 전체 입력·캐시 입력·출력·추론·보고된 비용으로 기록한다. 실패·재시도한 호출의 사용량도 포함한다.
- H4(가드): 인증·설정 오류는 첫 번에, 호출이 연달아 3번 실패하면, 실행 상한(호출 수·입력 토큰)에 닿으면 일시정지하고 이유를 남긴다. 실행 목록과 상세에 표시된다.
- M7: 마이그레이션 전 백업과 외래 키 검사.
- M14(일부): 목 LLM 프로필(고정 토큰·캐시·지연·결함 주입·`/__stats`), 서버 스키마 대조 테스트, 현실형 샘플(9천·5만 줄).

### 0단계에서 새로 드러난 것
- **M2를 현실형 데이터에서 확인했다.** 5만 줄 현실형 샘플(허브 83개)에서 장면 연결 계산이 120초 걸렸다. 이 계산이 가져오기 요청 안에서 동기로 돌아 서버 전체가 멈췄다. 계산을 레이아웃 워커로 옮겨 가져오기 응답을 123초에서 4.4초로 줄였고, 계산하는 동안 다른 요청은 6ms 안에 응답한다. 계산량 자체는 그대로다. 근본 수정(허브를 장면 그래프의 노드로 표시)은 5단계에서 한다.
- **M3를 현실형 데이터에서 확인했다.** 허브 간선이 있는 현실형 샘플은 9천 줄에서도 대화 그래프 레이아웃이 메모리 부족(4GB)으로 실패한다. 이제 서버는 죽지 않고 '실패'로 표시하지만, 그래프 화면은 비어 보인다. **5단계에서 우선순위를 높여 다룬다.**
- 결함 주입 실행(9천 줄, 누락 5%·형식 오류 2%·잘림 1%)에서 7,459줄 중 1,568줄이 실패로 끝났다. 빠진 줄 재요청과 형식 오류 분할 재시도(2단계 H5)가 아직 없기 때문이다. 요청당 줄 수는 1줄 304회, 2줄 218회처럼 작은 요청이 많았다(2단계 H1).

### 2단계와 허브 그래프 (2026-10-12)
- **묶음과 계획**
  - 연속 장면을 묶는 묶음 계획을 넣었다.
  - 실행 시작 때 번역 계획을 저장한다. 연관도는 대본 순서, 종류, 화자 겹침, 대사 그래프의 직접 연결로 판단한다.
  - 노드별로 계획 묶음 단위로 보내고, 작은 조각은 이웃 묶음에 붙인다.
  - 빠진 줄과 일시 실패한 줄은 대기열로 돌려보내고, 형식 오류는 반으로 나눠 다시 보낸다.
- **칸 배분**: 계정별로 칸을 두고, 단계마다 차례로 칸을 준다.
- **전역 순번·알림·캐시**: `units.seq`를 넣었고, 알림을 합치고, 용어·자료 조회를 캐시한다.
- **번역 준비**: 계획, 노드별 요청, 고정 토큰 실측, 경고, 1.3배 상한을 2단계 실행 대화상자로 보여 준다. 고정 토큰을 잰 적 없는 연결이 있으면 입력 상한을 비워 둔다.
- **목표 달성**: `pnpm budget` 기준(9,040줄, 요청당 고정 2만 토큰)으로 측정했다.
  - 번역 호출 2,565 → 440회
  - 5줄 이하 호출 59% → 0%
  - 결함 주입 실패 24.8% → 0.1%
  - 번역 준비 예측: 첫 AI 노드는 정확하고, 이력 한 번 뒤로는 모든 노드가 ±20% 안에 든다.
- **뺀 것**
  - 사람 수정 보호: 적용은 사용자가 워크플로에 넣은 동작이다.
  - 묶음 출력을 한 번만 저장하기: 스크립트가 줄마다 출력을 읽는다. 3단계로 미뤘다.
- **M2·M3 (허브 그래프)**
  - 장면 그래프의 허브는 '연결점' 노드로 두고, 대사 그래프의 허브 간선은 배치에서 빼 직선으로 그린다.
  - 현실형 9천 줄: 1.7초. 이전에는 대사 그래프가 메모리 부족으로 실패했다.
  - 5만 줄: 14초. 이전에는 장면 그래프가 120초, 대사 그래프는 실패였다.
  - 앞 장면 문맥에서 허브를 거친 연결도 뺐다.
