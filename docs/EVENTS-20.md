## 저장 한 번 (대사 하나 고치고 Ctrl+Enter)

| | 요청 | 같은 요청 반복 | 반복분 서버 시간 · 크기 |
|---|---|---|---|

원인: 저장 응답의 `x-changed`로 `units·statuses·workflows`를 바로 다시 받은 뒤, 같은 변경의 SSE 이벤트(약 300ms 뒤, 묶음 250ms)가 같은 질의 7개를 다시 받았다. 주석은 "이미 받은 것은 다시 받지 않는다"고 했지만 그런 구분이 없었다.

고친 방법: 탭마다 id를 붙여 보낸다(`x-client`). 서버는 묶은 이벤트 안의 변경이 **모두 한 탭의 요청이 응답하기 전에 만든 것**이면(= 그 응답들의 `x-changed`에 다 들어 있으면) 이벤트에 `origin`으로 그 탭을 적는다. 그 탭은 이벤트를 건너뛰고, 다른 탭은 그대로 받는다. 실행·채팅처럼 응답 뒤에 이어지는 작업, id 없는 요청, 다른 탭의 변경이 하나라도 섞이면 `origin`이 없어 지금처럼 모두 다시 받는다. 다른 탭에서 확인: 저장한 탭 말고 다른 탭이 질의 5개를 다시 받고 새 번역을 보였다.

`runs → analysis`처럼 다른 주제를 따라가는 질의(`ALSO`)는 이벤트에만 있었는데, 이제 `x-changed`에도 같이 적용한다(`refetchKeys`).

## 실행 중 (기본 번역, 장면 12개 · 314줄, mock)

이벤트 14개가 약 650ms 간격(서버 묶음 300ms·최대 1s + 클라이언트 250ms)으로 와서, 하나에 질의 8개(대사 목록 100줄, 장면 목록, 상태별 개수, 화자, 실행·작업·분석 목록, 프로젝트)를 다시 받는다. 합계 GET 112개, 서버 시간 합 3.9s(질의당 평균 35ms), 같은 변경을 두 번 받는 것은 없다.

판단: 그대로 둔다. 실행 중 화면이 번역·개수를 실시간으로 보이는 것이 목적이고, 묶음이 초당 1.5번 이하로 막고 있다. 상태 정의와 대사별 집계를 나누면(`units → statuses`) 이벤트마다 `statuses` 한 개(평균 36ms)를 덜 받을 뿐이라 질의 키를 나누는 복잡성에 비해 이득이 작다. (2026-10-31: 나눴다. 개수가 `units` 아래로 가자 줄 변경이 워크플로 검사까지 다시 받게 하던 `statuses → workflows`도 끊겼다. "브라우저 공책 후" 참고.)

## 채팅 한 턴 (mock, 도구 없이 답만)

요청 25개: 스트림 응답의 `x-changed`(5) → 턴 끝 `notifyChanged(CHAT_TOPICS)`(15) → SSE 이벤트(5). 반복은 10개, 서버 시간 약 0.5s.

판단: 그대로 둔다. 스트림은 응답한 뒤에 바뀌므로 이벤트에 `origin`이 붙지 않는다. 턴 끝의 넓은 갱신은 이벤트 스트림이 조용히 끊긴 경우를 위한 것이다(도구가 무엇을 바꿨는지 응답이 말할 수 없다). 턴마다 한 번, 모델 응답 시간(초 단위)에 비하면 작다.

**실행 중 워크플로 화면(15초)**: 59KB → 31KB. 줄 변경이 `statuses`를 거쳐 워크플로·워크플로 목록을 다시 받던 것(23KB·5KB씩 5번)이 없어졌다.

**다시 그리는 수(StrictMode라 2배로 셈)**: 다른 탭에서 줄 하나 수정 → 100줄 중 1줄. 줄 고르기 → 2줄. 인물 프로필 수정 → 인물 표 20줄 중 1줄, 쌍 표 0쌍. 관계 수정 → 40쌍 중 1쌍. 용어 수정·확정 → 그 행만(전: 표 전체). 전에는 대본의 태그 목록이 그릴 때마다 새로 만들어져 100줄이 모두 다시 그려졌다.

**반응**: 다른 탭의 수정이 0.46초 뒤 보임(묶음 300ms 포함). 확정·확인함 117ms. 189줄 일괄 태그는 서버 응답(0.44초) 전 0.38초에 보임(개발 모드에서 보이는 98줄을 두 번 그리는 시간).

**쓰기 비용(트리거)**: 9,040줄을 실행처럼 한 줄씩(제안 + 줄 + 태그) 저장할 때 줄당 0.313ms → 0.352ms, 9,040줄 한꺼번에 7ms → 15ms. 모델 호출(초 단위)에 비하면 영향 없음.
