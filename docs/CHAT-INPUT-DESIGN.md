# 채팅 입력 다시 설계 (검토용 초안)

> 상태: 확정·구현됨 (5장 결정 반영). 4장 표에서 완료 여부를 본다.
> 원칙: 로직은 워크플로 한 곳에만 둔다. 채팅에 숨은 기능을 박지 않는다. 키보드만으로 끝까지 갈 수 있어야 한다.

## 1. 번역가가 채팅에 묻는 것과 필요한 것

| # | 이런 질문 | 가리킬 대상 (`@`) | 에이전트가 쓸 도구 | 지금 있나 |
|---|---|---|---|---|
| 1 | 이 대사 무슨 뜻이야? 말장난이야? | 대사 | `read_line`, `line_context` | 있음 |
| 2 | 이 장면 앞에서 무슨 일이 있었지? | 장면 | `read_scene`, `list_events` | 있음 |
| 3 | 지금 누구한테 하는 말이야? | 대사 | `read_line` (청자), `line_context` | 있음 |
| 4 | Gentleman이 Lookout한테 앞에서 존댓말 썼어? | 인물 2명, 또는 관계 | `find_lines` (speakers + listeners), `list_speech_rules` | 있음 |
| 5 | 'The Rat'을 지금까지 어떻게 번역했어? | 용어, 또는 검색어 | `term_usage`, `find_lines` (q) | 있음 |
| 6 | 이 인물 말버릇 예시 몇 개 보여 줘 | 인물 | `find_lines` (speakers), `list_characters` | 있음 |
| 7 | 이 대사 번역 후보 세 개, 톤 다르게 | 대사 | 답변만 + 고르면 `propose_translation` | 있음 |
| 8 | 이 장면 번역 읽고 어색한 곳 짚어 줘 | 장면 | `read_scene` + `propose_changes` | 있음 |
| 9 | '금고털이'를 전부 '금고 전문가'로 바꿔 줘 | 검색어 (또는 용어) | `find_lines` (q) + `propose_changes` | 있음 |
| 10 | Mole이 Gentleman한테 반말한 대사 다 고쳐 줘 | 인물 2명 | `find_lines` + `propose_changes` | 있음 |
| 11 | 검토 필요 대사를 이유별로 묶어 줘 | 상태, 태그 | `find_lines` (statuses, tags, marks) | 있음 |
| 12 | 어느 장면이 제일 덜 됐어? | 없음 | `project_overview`, `list_scenes`, `script_stats` | 확인 필요 (장면별 상태 집계가 있는지) |
| 13 | 방금 돌린 워크플로, 왜 실패가 많아? | 실행 기록 | `read_run` | 있음 (재요청 이유까지 나오는지 확인 필요) |
| 14 | 이 장면만 다시 번역해 줘 | 장면 + 워크플로 | `start_run` (사용자 승인) | 있음 |

**결론**
- 질문 대부분은 지금 도구로 답할 수 있다.
- 부족한 것은 "무엇을 묻는지 정확히 가리키는 방법"(`@`)이다.
- 12번과 13번은 실제 모델로 물어 확인한다(가짜 AI로는 확인 불가).

## 2. `@` 첨부

### 2-1. 고를 수 있는 종류

| 종류 | 무엇으로 찾나 | 목록에 보이는 모양 | 첨부하면 에이전트가 받는 것 |
|---|---|---|---|
| 대사 | 키, 원문, 번역문 (전문 검색 색인) | `REEVE · c1.ferry.002 · Excuse me. I have…` | 대사 id, 키 |
| 장면 | 제목, 키 | `Chapter 1 › Greywater Ferry · 11줄` | 장면 id |
| 인물 | 이름, 별칭 | `Lookout · 주연 · 별칭 The Lookout` | 인물 id |
| 관계 | 두 사람 이름 | `Lookout → Gentleman · 협력자 ▸ 배신자` | 관계 id |
| 말투 규칙 | 화자·청자 이름 | `Mole → Gentleman · 해요체` | 규칙 id |
| 사건 | 제목, 관련 인물 | `요트 탈환 · Lookout, Gentleman` | 사건 id |
| 노트 | 제목 | `작품 개요` | 문서 id |
| 용어 | 원문, 번역어 | `The Rat → 쥐새끼` | 용어 id |
| 태그·상태 | 이름 | `#청자 미상 · 120줄`, `검토 필요 · 218줄` | 태그·상태 id (대사 묶음으로 쓰임) |
| 워크플로 | 이름 | `인물·관계 추출` | 워크플로 id |
| 실행 기록 | 시작 시각, 워크플로 이름 | `10/23 11:02 · 번역 · 실패 12` | 실행 id |

### 2-2. 흐름

```
@           → 맨 위: 지금 화면에 있는 것 (보고 있는 장면, 고른 대사, 열린 인물…)
              그 아래: 종류 목록 (대사 · 장면 · 인물 · …)
@lo         → 종류마다 상위 3개씩, 종류별로 묶어서
              (묶음 제목 줄에서 Tab → 그 종류만 보기)
@인물 lo    → 인물만, 상위 20개. 맨 아래 "더 보기"
```

- 검색은 항상 서버에서 한다. 한 번에 가져오는 개수는 종류당 최대 20개다.
- 정렬: 이름이나 키가 정확히 맞는 것 → 앞부분이 맞는 것 → 포함하는 것 → 최근에 본 것.
- 대사 3만 줄, 용어 2천 개도 같은 방식으로 동작한다. 목록에 전부 올리지 않는다.

### 2-3. 키보드

| 키 | 동작 |
|---|---|
| ↑ / ↓ | 이동. **고른 줄이 늘 보이게 목록이 따라 스크롤** |
| Enter | 고르기 → 칩으로 붙고 입력창으로 돌아감 |
| Tab | 묶음 제목에서: 그 종류만 보기. 항목에서: Enter와 같음 |
| Shift+Tab / Backspace (검색어가 비었을 때) | 종류 좁히기를 풀고 한 단계 위로 |
| Esc | 목록 닫기 (한 번 더 누르면 답 중단, 지금과 같음) |

### 2-4. 칩

- 입력창 위에 `대사 REEVE: Excuse me…` 식으로 붙고, ×로 뺄 수 있다.
- 보낸 메시지에도 칩이 남아서 무엇을 가리켰는지 나중에 볼 수 있다. 지금은 사라지는데, 이것도 고친다.
- 칩을 누르면 그 대상 화면으로 이동한다.

## 3. `/` 명령

### 3-1. 목록 = 이 프로젝트의 워크플로 + 저장한 지시

```
/
 워크플로
  /번역              번역하고 검수까지. 못 넘으면 검토 필요로
  /청자 추정          대사마다 누구에게 하는 말인지 적기
  /인물·관계 추출      인물·관계·말투 규칙을 자료에 넣기
  /사건 추출          사건과 관련 인물을 자료에 넣기
  (사장님이 만든 워크플로가 있으면 여기에 함께)
 저장한 지시
  (프로젝트 설정에서 만든 것만. 앱이 기본으로 넣는 것은 없음)
```

- 앱에 박아 두는 명령은 없다. 워크플로를 만들거나 지우면 목록도 따라 바뀐다.
- 지금 있는 `/new`, `/rename`, `/model`, `/permissions`, `/stop`은 없앤다. 모두 버튼이나 Esc로 된다.

### 3-2. 워크플로 실행 흐름

```
/번역  → 대상 고르기가 바로 열림 (@의 장면·대사·태그·상태·인물만)
       → 대상 고르고 Enter
       → 채팅에 "실행 확인" 카드: 대상 N줄, 예상 요청 수, 예상 비용, [실행] [취소]
       → [실행]을 누르면 시작. 진행은 같은 카드에 실시간으로 표시
```

- 확인 카드는 지금 실행 창과 같은 계산(preflight)을 쓴다.
- AI 비용이 드는 일이라 확인 없이 바로 돌지 않는다.
- 대상 범위는 실행 창과 같다: 장면, 대사, 태그, 상태, 인물(그 인물의 대사).

### 3-3. 저장한 지시

- 이름과 지시문뿐이다(로직 없음). 고르면 지시문이 입력창에 들어간다.
- 지시문 안에 `{대상}` 자리가 있으면 그 자리에서 `@` 고르기가 바로 열린다.
  - 예: `/어색한곳` → "{대상}에서 말투가 어색한 곳을 짚어 줘" → 장면 고르기 → Enter로 보내기
- 관리: 프로젝트 설정 › 채팅. 지금 있는 화면을 그대로 쓴다.

### 3-4. 키보드

| 키 | 동작 |
|---|---|
| `/` (입력창 맨 앞) | 목록 열기 |
| 글자 | 이름으로 거르기 (한글 초성 검색은 하지 않음) |
| ↑ / ↓, Enter, Esc | `@`와 같음. 고른 줄이 늘 보이게 스크롤 |

고른 뒤에는 포커스가 항상 입력창(또는 이어지는 대상 고르기)에 남는다. 마우스로 돌아갈 일이 없어야 한다.

## 4. 지금 구현에서 바꾸거나 지울 것

| 지금 | 바꾼 뒤 | 상태 |
|---|---|---|
| `@`가 대사·장면·인물·용어·문서를 한 목록에 섞어서 보여 줌 | 2장의 흐름 (지금 화면 → 종류 → 서버 검색) | 완료 |
| 인물(목록에는 있으나 일부 프로젝트에서 0), 관계, 사건, 말투 규칙, 태그·상태, 워크플로, 실행 기록 없음 | 추가 | 완료 (`GET /projects/:id/chat/attach`, 12종) |
| 방향키로 움직여도 스크롤이 따라오지 않음 | 따라오게 | 완료 (`scrollIntoView({ block: 'nearest' })`) |
| 보낸 메시지에 칩이 안 남음 | 남김 | 완료 (`message.metadata.chips`, 칩을 누르면 그 화면으로) |
| `/new` `/rename` `/model` `/permissions` `/stop` | 삭제 | 완료 |
| `/`에 워크플로 없음 | 3장의 흐름 | 완료 (대상 고르기 → 실행 확인 카드 → 진행) |

## 5. 열린 질문 → 결정

1. **`{대상}`**: 쓴다. 저장한 지시를 고르면 첫 `{대상}` 자리에서 `@` 고르기가 열리고, 고른 항목은 칩으로 붙고 그 자리는 짧은 이름으로 바뀐다. `{대상}`이 둘 이상이면 다음 자리가 이어서 열린다.
2. **실행 확인 카드**: 대상을 카드에서 바꾸지 않는다. 바꾸려면 [취소]하고 처음부터 다시 한다.
3. **`@` 종류**: 2-1의 12종을 모두 둔다 (태그와 상태는 각각 한 종류).
4. **칩을 누르면**: 그 항목의 화면으로 이동한다 (링크처럼 기록에 한 칸 쌓임).

### 구현 메모

- 대상 범위: 워크플로가 대사를 받으면 장면·대사·태그·상태·인물(그 인물이 말한 대사), 용어를 받으면 용어. 장면과 대사(인물)는 범위가 서로 좁혀지므로 함께 고를 수 없다 (한쪽을 고르면 다른 쪽은 목록에서 빠진다).
- 실행 확인 카드는 대화 기록(`chat_sessions.messages`)에 들어간다: `data-run` 부분 하나를 가진 사용자 메시지(`metadata.kind = 'run-card'`)로, 만든 자리에 그대로 있다. 그래서 탭을 닫거나 다른 기기에서 열어도 보이고, `chat` 토픽으로 다른 창에 바로 반영된다.
  - 담는 것: 워크플로 id·이름, 입력 종류, 고른 칩, 대상 범위(scope), 카드에 보인 실행 전 계산(대상 수, 요청 수, 시간, 비용, 권장 한도), 상태(`pending` → `started` | `cancelled`), 시작한 뒤의 runId, 만든 시각. 카드는 만들 때의 숫자를 그대로 보여 주고, 실행도 그 범위와 한도로 한다.
  - 서버: `POST /chat/:id/run-cards`(칩에서 범위를 풀고 preflight를 계산해 카드를 만든다), `POST /chat/:id/run-cards/:cardId/start`(실행을 시작하고 runId를 카드에 적는다. 한 번의 호출), `.../cancel`. 대기(`pending`) 상태에서만 바뀌고 이미 답한 카드나 동시에 두 번 누른 실행은 400.
  - 에이전트는 카드를 "사용자가 이 대화에서 워크플로 '번역'을 장면 X(12줄)에 실행함 · run <id> · 상태" 한 줄로 읽는다(대기·취소 포함, 사용자 메시지 자리에). 시작한 실행은 `read_run`으로 결과를 본다. 대화 압축은 카드를 이 한 줄 크기로 센다.
  - 답이 진행되는 동안 만들거나 답한 카드는 답 저장 때 지워지지 않는다(`withStoredCards`). 다시 생성은 카드를 지우지 않고, 카드는 이어서 답하는 메시지(도구 승인 응답)나 새로 보낼 메시지로 취급되지 않는다.
  - 화면: 카드는 `useChat`의 메시지 목록에서 그린다. 답이 스트리밍 중이 아닐 때 저장된 대화의 카드를 목록에 맞춰 넣는다(`syncCards`). 진행률은 실행 자체의 데이터(`runs` 토픽)에서 온다.
  - CLI 채팅은 이미 본 카드의 상태 변화를 다시 받지 못한다(새 카드와 새 메시지만 이어서 받는다). 필요하면 에이전트가 `read_run`으로 확인한다.
- 정렬: 이름·키가 정확히 같음 → 앞부분 → 포함 → 그 밖의 칸(별칭, 본문)에서만 맞음, 같은 단계에서는 최근 바뀐 것. 대사는 키가 맞는 것, 그다음 대본 순서.
- 실행 기록 목록은 열 때마다 다시 읽는다 (실행 진행이 목록 전체를 새로 고치게 만들지 않으려고 `units` 쪽 암시에 넣지 않았다).
