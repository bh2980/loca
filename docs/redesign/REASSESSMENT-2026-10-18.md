# A/C 개편 재점검 — 공통화 이후에도 남은 문제

날짜: 2026-10-18. 기준: `codex/ui-redesign-ac`의 현재 미커밋 작업 상태. 이전 점검 기록의 ‘수정됨’ 표시는 그때 검증한 개별 조건의 결과이며 디자인 완성을 뜻하지 않는다.

사용자가 추가 구현보다 가설 검증과 문제 취합을 먼저 요청했다. 구현 작업자들을 중단했고 **이번 재점검에서 제품 코드는 수정하지 않았다.** 아래는 해결 보고나 구현 승인 요청이 아니다. 기존 변경은 유지했다.

## 놓친 검증 기준

이전에는 공통 컴포넌트 사용 여부, 요청한 단일 동작의 정상 완료, 타입/테스트 통과를 중심으로 확인했다. 그 결과 다음 질문이 빠졌다.

- 같은 목적의 부품들이 정말 같은 높이·표면·상태·간격 규칙을 사용하는가? 같은 primitive를 쓴다는 것만으로 충분하지 않다.
- 사용자가 기능 위치를 모르는 상태에서도 목표 동작을 찾을 수 있는가? 안내받은 경로를 수행할 수 있다는 것과 다르다.
- 화면이 주는 약속(팝업, 권한, 모델 설정)이 실제 동작과 일치하는가?
- 단건/일괄, 마우스/단축키, 모델 있음/없음, 대사/UI 문자열 등 서로 다른 경로가 같은 정책을 따르는가?
- 현재 화면의 대상·선택·사용자 정의 워크플로가 실제 실행 범위와 연결되는가?

## 가설과 검증 방법

| 가설 | 확인 방법 | 판정 |
|---|---|---|
| H1. 공통화가 import/스타일 재사용에 머물고 의미별 조합 규칙은 분열되어 있다 | 탭/버튼 DOM 실측, 표 조상 스타일, 상세 섹션 좌표, 공유 부품 비교 | 확인: V1–V4 |
| H2. 기능 성공 경로만 확인해 발견성과 열고 닫는 동작을 놓쳤다 | 설정 항목 선택·바깥 클릭·Escape, 테마 탐색, 모델 없는 AI 클릭/단축키 | 확인: N1–N2, A1–A2 |
| H3. 설정은 사용자 정책보다 내부 구현 구조를 그대로 드러낸다 | 권한 화면·schema·카탈로그 비교, 메모리 DB의 제안/수락 경로 실험 | 확인: P1–P3, S1 |
| H4. 분석 기능은 엔진보다 템플릿·진입점·선택 범위 연결이 부족하다 | 자료 분석 팝업, 새 워크플로 폼, 노드 라이브러리, 실행 API/엔진 확인 | 부분 확인: W1–W2. ‘세부 분석 자체가 불가능’은 아님 |
| H5. 같은 상세 부품을 쓰면 대상별 정보 적합성도 해결된다고 가정했다 | 중계소 UI 문자열의 실제 상세 화면 확인 | 확인: C1 |

## 확인된 문제

### V1 · P2 · 같은 보기 전환에 두 가지 크기·테두리 규칙

- 현실형 인물·관계에서 그래프/인물 표/관계 표는 **36px** 높이, 옆 ‘인물’ 버튼은 **28px**로 실측됐다. 보기 그룹은 외곽 테두리/패딩 외에 각 항목에도 테두리를 가진다.
- `ViewSwitch`는 `ToggleGroup variant="outline"`을 사용하면서 size를 지정하지 않는다. 자체 테두리와 item 테두리가 겹친다. 대사 보기의 `SegmentedControl`은 별도 32px 바깥면/28px 항목 규칙이다.
- 범위: 자료의 인물·관계/사건 보기와 원본 그래프 보기. 단순히 한 화면의 높이만 수정하면 같은 문제가 남는다.
- 근거: `packages/ui/src/layout/view-switch.tsx:5`, `packages/ui/src/layout/segmented-control.tsx`, `packages/ui/src/primitives/toggle.tsx`, `apps/web/src/routes/p.$projectId.knowledge.tsx:371`, `apps/web/src/routes/p.$projectId.graph.tsx:76`.
- 수용 기준: 같은 헤더의 보기 전환과 동작 버튼에 공통 크기 기준을 적용하고 A/C에서 선택/hover/focus/비활성까지 비교. 콘텐츠 탭과 보기 전환을 무조건 동일 컴포넌트로 합치는 것은 별도 판단이다.

### V2 · P2 · 상태·태그 표의 ‘컨테이너’를 폭 제한으로만 구현

- 표가 작아졌지만 표를 감싼 스크롤 영역은 실측 **border 0px, radius 0px, 투명 배경**이다. 표 주변을 하나의 설정 영역으로 읽게 하는 외곽선/표면이 없다.
- `SettingsContent`는 여백·너비·스크롤만 소유하고, `DataTable`은 설정용 프레임을 소유하지 않는다. 두 부품 사이의 책임이 비어 있다.
- 근거: `packages/ui/src/layout/settings-content.tsx:4`, `packages/ui/src/data/data-table.tsx:258`, `apps/web/src/routes/p.$projectId.settings.statuses.tsx:224`.
- 수용 기준: 제목·추가 동작·표가 같은 프레임에 속하는 공통 설정 컬렉션 계약. 모든 전체 폭 표에 일괄 테두리를 추가하는 수정은 피한다.

### V3 · P2 · 같은 Inspector 안에서 섹션 시작선이 24px 다름

- ‘화자와 청자/앞뒤 대사/검사 요약’ 트리거 x=2249.02, ‘추가 정보/실제 AI 문맥’ x=2225.02: **24px 차이**. 제목 두께도 각각 650/500으로 다르다. 높이는 둘 다 28px여서 높이만 맞추는 검증으로는 발견되지 않는다.
- 앞쪽은 `InspectorSection`의 px-6/py-3/하단 경계, 뒤쪽은 인셋 없는 기본 `AdvancedDisclosure`다. 추가 정보 안에는 InspectorSection이 다시 들어가 단순 바깥 padding 추가는 중첩 들여쓰기를 만들 수 있다.
- 근거: `apps/web/src/components/line-detail.tsx:159,179`, `packages/ui/src/inspector/advanced-disclosure.tsx:7`, `packages/ui/src/inspector/inspector-section.tsx:18`.
- 수용 기준: 접힘/펼침 모두 같은 시작선·경계·제목 위계. 번역 입력 아래의 인라인 disclosure까지 같은 인셋으로 확대하지 않는다.

### V4 · P1 · 허용된 최소 도크 폭에서 인물 문체 선택값이 사라짐

- 추가 캡처 검토 중 발견해 브라우저에서 계측했다. 현재 도크 폭은 **279.98px**, ‘문장 길이/힘/꾸밈’ Select 각각 **30.33px**, 값 span은 **0px**다. 접근성 트리에는 ‘보통’이 있지만 화면에서 값은 읽을 수 없다.
- 도크는 280px를 정상 최소 폭으로 허용한다. PropertyGrid의 라벨 열/24px 인셋 안에 복합 문체 입력이 고정 3열로 들어가 값 영역이 소진된다. 단순 창 너비뿐 아니라 실제 패널 너비를 기준으로 입력 배치를 바꾸어야 한다.
- 근거: `packages/ui/src/layout/right-dock.tsx:96`, `packages/ui/src/inspector/property-grid.tsx:6`, `apps/web/src/components/knowledge/editor.tsx:190–192`.
- 수용 기준: 허용되는 모든 도크 폭에서 선택값과 이름이 읽혀야 한다. 패널 폭 보존 테스트와 내용 가독성 검증은 별개다. 최소 폭 확대나 복합 필드 재배치 중 실제 요구에 맞는 공통 규칙을 정해야 한다.

### N1 · P2 · 설정이 팝업처럼 보이지만 닫히는 계약이 없음

- 설정 → 상태·태그를 눌러 이동해도 열린 채다. 본문 제목 클릭과 Escape에도 열린 상태가 유지됐다. 이후 다른 작업 화면으로 이동해도 메뉴가 남았다.
- 원인은 `CollapsibleContent`를 absolute bottom-full로 띄운 것이다. Collapsible에는 팝업의 outside click/Escape/focus 복귀 동작이 없고 항목 선택도 닫힘 상태를 갱신하지 않는다.
- 근거: `apps/web/src/components/app-sidebar.tsx:51–75`.
- 수용 기준: 트리거 하단 고정/위로 열림을 유지하면서 항목 선택·외부 클릭·Escape로 닫힘. 마우스와 키보드 모두 확인.

### N2 · P2 · 테마 제어는 있으나 설정에서 발견할 수 없음

- 프로젝트 이름 메뉴에 ‘밝게/어둡게/시스템 설정’이 있고 실제 전환은 정상이다. 설정 메뉴에는 테마가 없다.
- 따라서 기능 부재가 아니라 위치와 범위의 문제다. 화면 테마를 바꾸려는 사용자가 프로젝트 전환 메뉴를 열어야 한다.
- 근거: `apps/web/src/components/app-sidebar.tsx:33,89`, `apps/web/src/lib/nav.ts:39`.
- 수용 기준: 사용자가 외형 설정을 찾는 위치에서 테마를 발견하고 현재 선택을 확인할 수 있어야 한다.

### A1 · P2 · 자주 쓰는 다듬기보다 모델 설정이 메뉴를 차지함

- 모델이 있는 경우 다듬기는 더보기 안에만 있다. 모델이 없는 중계소의 빈 번역에서는 더보기에 **‘편집기 AI 모델 설정’ 하나만** 있었다.
- AI 번역은 별도 팝오버 → 설정 링크를 거친다. 미설정 상태에는 다듬기 자체가 숨겨진다. 버튼 크기 공통화는 되었지만 동작 우선순위와 미설정 진입 정책은 공통화되지 않았다.
- 근거: `apps/web/src/components/translation-editor.tsx:231–251`.
- 수용 기준: 번역·다듬기의 직접 노출, 모델 미설정의 동일한 설정 진입 정책, 실제 항목이 없는 더보기 제거. 모델을 관리하는 설정 화면과 행 안의 중복 설정 항목은 구별해서 판단.

### A2 · P2 · 모델 없는 AI 단축키는 아무 피드백도 없음

- 중계소 UI 문자열의 빈 번역 칸에서 Alt+.를 눌러도 접근성 트리와 화면에 변화가 없었다. 마우스 AI 번역은 설정 안내를 표시한다.
- 같은 명령의 handler는 모델이 없으면 즉시 반환한다. 클릭과 단축키가 서로 다른 진입 정책을 갖는다.
- 근거: `translation-editor.tsx:108–110,187`.
- 수용 기준: 단축키/클릭 모두 동일한 미설정 안내와 설정 진입, 초안 보존. 실행 중·실패·재시도까지 별도 상태로 검사.

### P1 · P1 · 원하는 대상별 생성/변경/삭제 권한을 표현할 수 없음

- 현재 열은 읽기/변경/실행/삭제이며 생성은 변경에 포함된다. 자료는 인물·관계·말투·사건·문서가 한 행이고, 삭제는 자료·용어·태그를 합친 별도 ‘항목 삭제’ 행이다.
- ‘용어 삭제 허용, 태그 삭제 금지’나 ‘인물 조회·수정 허용, 생성 금지’를 표현할 수 없다. `delete_items`는 kind만 바꿔 양쪽을 삭제한다.
- 메모리 DB에서 동일 도구의 terms/tag 제안 둘 다 수락 후 삭제되는 것을 확인했다. 실제 프로젝트 항목은 삭제하지 않았다.
- 근거: `packages/shared/src/agent.ts:8–26,48–65`, `apps/server/src/services/agent-tools.ts:662`, `apps/web/src/components/settings/agent-tab.tsx:107`.
- 수용 기준: 대상×생성/조회/변경/삭제를 사용자 정책의 기준으로 삼고, 실제 지원하지 않는 동작은 정직하게 표시. 워크플로 ‘실행’은 CRUD 외 추가 동작으로 유지할 이유가 있으므로 존재 자체를 결함으로 보지는 않는다.

### P2 · P1 · 단건 도구 끄기가 같은 행위의 일괄 경로에는 적용되지 않음

- :memory: DB에서 `disabledTools=['save_character']` 설정 → 단건 도구는 카탈로그에서 사라짐 → `save_knowledge.characters` 제안 생성 → 수락 → **인물 생성과 프로필 변경 모두 성공**.
- 반대로 일괄 도구만 끄면 단건 도구는 남는다. 구현은 정확한 도구 이름의 노출을 제어하므로 동작 자체는 현 모델과 일치하지만, ‘권한’ 화면에서 사용자가 기대하는 행위 제한과 다르다.
- 모든 변경은 실제 `proposeChange → decideProposal` 경로로 검증했다. 제안/수락 절차를 우회했다는 주장은 아니다. 앱에서 사용자가 직접 편집할 권한과도 별개다.
- 근거: `agent-tools.ts:627,643,682`, `agent-catalog.ts:27`, `proposals.ts:76`.
- 수용 기준: 단건/일괄 도구 모두 실제 payload의 대상·행위로 같은 권한을 검사. 이름만 재분류해서는 해결되지 않는다.

### P3 · P2 · ‘우회 모드 한도’의 목적·적용 조건이 불명확

- 현재 기본 모드가 ‘수락/거절’인데 우회 변경 수·비용 필드가 항상 나타난다. 모드 메뉴는 ‘묻지 않고 모두 바로 반영’이라고 설명하지만 실제 한도에 닿으면 다시 묻는다.
- 코드에서 한도는 대화가 bypass인 경우 다음 변경을 자동 적용할지 결정하는 기준이다. 전체 AI 지출을 멈추는 하드 예산이 아니며, 보고되지 않은 비용도 포함하지 못한다.
- 한도 자체가 무의미한 것은 아니다. 자동 반영의 범위를 제한하는 기능인데 현재 이름·상시 노출·모드 설명으로 목적을 이해하기 어렵다.
- 근거: `agent-tab.tsx:59–85`, `packages/shared/src/agent.ts:90–99`, `change-gate.ts:55–85,97–111`.
- 수용 기준: 무엇을 자동 반영하고 언제 다시 확인하는지 사용자 언어로 설명. 관련 모드와 한도를 함께 배치하고 실제 과금 상한처럼 표현하지 않는다.

### S1 · P2 · ‘편집기 AI’ 설정에 워크플로 자료 자동 확정까지 섞임

- ‘편집기 AI’를 열면 모델/자동완성 다음에 ‘AI가 만든 것을 바로 확정’이 있고 인물·관계·사건·문서·용어의 자동 확정을 바꾼다. 이 설정은 작품 분석과 워크플로 결과에 적용된다.
- 다른 화면은 같은 경로를 ‘AI 사용 방식’이라고 부른다. 에이전트 권한 모드와 이 자동 확정은 서로 다른 적용 경로지만 사용자에게 둘의 범위를 쉽게 비교할 구조가 없다.
- 근거: `apps/web/src/routes/p.$projectId.ai.usage.tsx:18–27`, `apps/web/src/components/settings/ai-confirm.tsx:28`, `apps/web/src/lib/nav.ts:43`.

### W1 · P1 · 자료 화면의 작품 분석은 기본 워크플로로 고정됨

- 인물 화면에서 더보기 → 작품 분석을 열면 기본 작품 분석 링크, 모델, 시작만 보인다. 세부 분석 워크플로 선택 UI가 없다. 현재 선택한 인물이나 탭이 분석 대상의 선택으로 연결되지 않는다.

### W2 · P2 · 세부 분석 지원이 템플릿·라이브러리에 명시적으로 드러나지 않음

- 다만 ‘인물 분석/사건 분석/작품 개요’라는 즉시 선택 가능한 시작점은 없고, 캔버스 AI 라이브러리에도 분석 항목은 없다. AI 자유 형식에서 출력 종류를 바꿔야 한다. ‘작품 분석 반영’ 저장 노드만 명시적으로 보여 비대칭이다.

## 추가 조사 필요 — 확정 문제와 구분

- AI 연결/API 키 설정 목록도 caller가 외곽 표면을 소유하는 구조다. 상태·태그와 같은 화면 계약이 필요한지 시각 비교가 더 필요하다. 전체 DataTable 결함이라고 일반화하지 않았다.

1. 시각 계약: 같은 역할은 하나의 크기·표면·인셋 규칙을 소유한다. 부품 하나만 보는 대신 같은 헤더/패널의 이웃 부품을 비교한다.

### 통합 검사에서 추가로 발견한 원인

- 전체 회귀 재실행에서 되돌리기 테스트가 간헐적으로 실패했다. 줄의 충돌 검사용 rev가 밀리초 시각이라 같은 밀리초 안에 일어난 ‘AI 제안 적용 → 사람 수정’을 구별하지 못했다. 테스트를 느리게 하는 대신 units의 갱신 rev를 DB 행 기준 `max(기존+1, 현재시각)`으로 증가시키도록 수정했다. 같은 시각/시계 역행을 고정한 회귀 테스트로 이후 사람 번역을 되돌리기가 덮지 못하게 검증한다.
