CLI account connection research — 2026-10-08

Status: research followed by implemented adapters and fake-process tests in src/auth.ts.
No real login, logout, account-status request, model request, credential-file read,
or token extraction was performed by this provider implementation task.
Commands executed: version/help, Codex's offline protocol schema generator, and a
read-only config/read projection of non-secret auth configuration. Only projected
setting names were printed during that last live CLI compatibility check.

1. Verified executable identity

Use the SAME resolved executable and CLI-owned authentication environment for login
and inference. Resolve once for a login attempt and pin the result until completion.
Do not assume a bare PATH command and a different npm installation share the same
version. The workbench currently resolves these local installations:
  Codex: Node + APPDATA/npm/node_modules/@openai/codex/bin/codex.js, 0.154.0
  Grok: USERPROFILE/.grok/bin/grok.exe, 1.0.30
  Antigravity: LOCALAPPDATA/agy/bin/agy.exe, 1.2.7
Connection fingerprints should include kind, resolved executable/prefix arguments,
and non-secret CLI auth-home overrides. Never include credential values.

2. Codex

Verified CLI help:
  codex login                 Browser ChatGPT OAuth login.
  codex login --device-auth   Device-code login.
  codex login status          Reports active authentication; documented exit 0 if signed in.
  codex logout                Clears stored authentication (not executed).

Preferred app UI interface: official Codex app-server JSON-RPC over stdio.
Installed 0.154.0's generated protocol schema confirms the following structures:
  initialize params: {clientInfo:{name,title?,version},capabilities?:{experimentalApi:false}}
  Then initialized notification.
  account/read params: {refreshToken:false}
    Response: {account:null|{type:'chatgpt',email:string|null,planType:string}|{type:'apiKey'}|...,
               requiresOpenaiAuth:boolean}
  account/login/start params: {type:'chatgpt'}
    Response: {type:'chatgpt',loginId,authUrl}
  account/login/start params: {type:'chatgptDeviceCode'}
    Response: {type:'chatgptDeviceCode',loginId,verificationUrl,userCode}
  account/login/completed notification: {loginId,success,error}
  account/login/cancel params: {loginId}
    Response: {status:'canceled'|'notFound'}
  account/logout params: omitted (not executed).

The browser opens authUrl; app-server owns callback/token persistence. The UI owns
pending/completed/cancelled states. Device code is a separate explicit flow; its
availability can depend on account/workspace settings. Do not silently switch flows.
Do not use token-import modes. No need to return tokens to the workbench frontend.
Current official documentation describes this auth surface for local/open-source
applications, which matches this workbench's current local scope.

3. Grok Build

Verified local CLI help and official docs:
  grok login                  Browser OAuth; --oauth is an optional explicit selection.
  grok login --device-auth    Device-code flow; --device-code is an alias.
  grok logout                 Clears stored credentials (not executed).

No dedicated auth-status CLI command appears in installed help or cited reference.
Do not invent `grok login status`, inspect auth.json, or report installation as login.
Browser login process can run from a click and exit on completion; capture only
sanitized progress fields, never raw stdout/stderr in app state or activity logs.
Fresh successful login exit is evidence that that attempt completed. After restart,
or absent a documented status probe, status must be unknown rather than signed out.
Device flow prints a verification URL and short user code according to official docs;
its exact terminal-output parsing must be tested against supported CLI versions.
No structured login-status protocol was established by this investigation.
`grok models` is not proven to validate authentication and is not a substitute.

4. Antigravity agy

Official supported flow: start interactive `agy`; if no reusable OS-keyring session
exists, the CLI opens the system browser for Google login. The CLI owns credentials.
The installed help has no login/auth/status/logout subcommands.
Logout is a TUI slash command: /logout. Do not pass it as a headless model prompt.
Official headless docs say missing authentication fails with authentication required;
headless inference must not be used merely to discover login status.

For current UI, provide a clearly labelled interactive-login route. A native terminal
or properly implemented PTY is required for a dependable TUI session; spawning it
with ordinary pipes and inventing completion detection is not an implemented flow.
Do not pretend the browser-only status contract is available for agy.
Do not set fake SSH variables or collect manual OAuth codes to emulate another flow.

5. Proposed provider/worker contract

AuthCapability:
  methods: ('browser'|'device-code'|'terminal')[]
  canReadStatus: boolean; canCancel: boolean; canLogout: boolean; detail: string
AuthState:
  state: 'unknown'|'signed-out'|'signed-in'|'pending'|'failed'
  method?: string; accountLabel?: string; checkedAt?: string; detail: string
AuthAttempt:
  id; connectionId; connectionFingerprint
  state: 'starting'|'waiting'|'succeeded'|'failed'|'cancelled'
  authUrl?; verificationUrl?; userCode?; message

inspectAuth(connection) -> capability + AuthState
startLogin(connection, {method, onUpdate, signal}) -> attempt lifecycle
cancelLogin(attemptId) -> cancel only this pending attempt

Worker API can expose status, start, poll/events, and cancel operations. Use POST
for starting/cancelling login; one pending attempt per resolved CLI/auth-home.
Changing connection settings supersedes that attempt's UI result.
Cancel/timeout stops the pending login, closes owned subprocesses and removes the
ephemeral UI link/code. Cancellation must never call logout on an existing account.
For Codex, use official cancel first; for CLI-only flows terminate the owned process
tree. In a success/cancel race, refresh observable status and avoid false signed-out.
Attempt URLs/codes stay in worker/frontend memory only, not the database, run logs,
analytics, browser localStorage or model context. No passwords or bearer tokens enter
the workbench UI. Provider-controlled error text is not blindly returned to clients.
General API credentials remain a separate connection type, not a CLI login substitute.
