# Translation Workbench working rules

- Product: user-defined translation statuses + workflow nodes between them that automate translation with AI. Story/world documents, characters, relationships and the dialogue/scene graphs exist to give AI nodes context. The current development spec is `docs/IMPROVEMENT-PLAN-2026-10-19.md`; everything it does not describe is legacy and may be removed or broken without compatibility shims.
- Check the complete journey in the browser (start the API, Vite and `pnpm mock-llm`), including native Back/Forward, retained filters/selection/drafts, and realistic volume (`pnpm samples -- --profile realistic --size 9000` → `samples/realistic-9k.json`; the mock LLM's `MOCK_PROFILE=cli-like|faulty` adds per-call overhead and failures). A successful build is not UX verification.
- URL search params are the source of truth for page state (filters, selection, tabs). Viewports and unsaved drafts live in sessionStorage; never push history entries for polling, panning or SSE refreshes.
- Server changes reach the browser over one SSE stream (`apps/server/src/events.ts`); never poll. Screens read rows from browser collections (TanStack DB: `apps/web/src/lib/collections.ts`, `terms.ts`, `knowledge.ts`, `units.ts`), one per kind and project; never copy those rows into a query cache. The row feed keeps them current: SQLite triggers note every changed row (`row_changed`, migrations from 0106) and each event carries the rows (lines as ids; the browser reads again the lines it holds). A table a screen shows gets triggers in a migration, never an emit at a write site. Writes go through the server API and the change gate, change the collection at once and finish when their `x-seq` comes back (`changeLines`, `decideItems`); no hand-written cache patches. Filters a screen and the CLI share live in `@tw/shared` (lines: `unitConditions` on the server). A screen's own question, answered anew each time it is asked (a filter's page of ids, a search or suggestions, a preview or preflight, the graph and route views), is a query whose key starts with its topic, refetched when the topic changes; `IMPLIES` covers one that reads another topic's tables. Row data still read through topic queries (connections, chat, saved graph views, the AI call log, and the app's own lists: projects and home defaults) is what is left of the old design: move it to collections, do not add more. Topics also stay for the CLI's waits.
- Labels must describe actual scope and evidence. Scene links are derived from the dialogue graph and must say so. Never invent graph edges or relationships.
- Prefer established libraries over custom infrastructure: ELK for layout (source graph is laid out once on the server, in a worker with a large stack), React Flow for small editable graphs, Canvas + d3-zoom + flatbush for the large source graph, AI SDK / TypeSafe SDK / execa for models, Zod for every boundary. Explain a concrete unmet requirement before writing a custom alternative.
- Source graphs read top-to-bottom; user workflows left-to-right. Do not reintroduce layer-width bounds, chain batching or component stacking that produce "staircase" layouts.
- UI: shadcn/ui components and the semantic tokens in `packages/ui/src/tokens/theme.css` only (light Slate + dark Night themes; never hex or Tailwind palette colours), one accent, color reserved for meaning, status as shape + colour (`StatusIcon`). Build screens only from the shared parts in `@loca/ui` (`DataTable`, `FilterBar`, `ActionBar`, `SelectionBar`, `Inspector`, `AiButton`): one primary button per screen/pane, buttons take no `size` (sm is the default), text sizes `text-base`/`text-sm`/`text-xs` only, no raw `<button>` or arbitrary `text-[Npx]`. Layout and text are said with `Box`/`Stack`/`Inline`/`Grid`/`Text`/`Heading` (props by token name: `gap`, `padding`, `tone`, `variant`…), never with `className`; what they cannot say becomes a component in `packages/ui` (see `packages/ui/README.md`, `pnpm storybook`). `pnpm ui-rules` refuses `className` anywhere in `apps/web`. Collections are tables; details open in a right-hand pane, not modals (AlertDialog only for destructive confirmation; the dialogue graph's translation card is a non-modal card anchored beside its node, not a detail view). The project chat is a global right-docked panel and every page reports its selection via `useReportView`. The app runs on Windows too: shortcut hints go through `keyLabel` (`lib/keys.ts`), never a hard-coded ⌘/⌥, and handlers accept Ctrl as well as ⌘.
- After `shadcn add`, replace any `from "cn"` import with `@/lib/utils` and remove the `cn` package it adds.
- Never run real AI jobs or modify user translations as part of verification without authorization; use the mock LLM and an isolated `WORKBENCH_DATA_DIR`.
- The `loca` CLI (apps/cli) is the main surface for coding agents: what the app can do should be doable from it, and the app is where people set things up and debug. The CLI and the chat tools share the server's agent tools and script service (`services/agent-tools.ts`, `services/script-query.ts`). Every change from the terminal goes through the change gate (`proposeChange`) and the project's terminal permission mode (ask / auto / bypass, set by a person in the app); never add a CLI path that writes around it (only saved graph views, pausing or cancelling a run, and making a new project from a file are direct). The CLI waits on the SSE stream, never by polling. Keep `.claude/skills/` (common rules in `.claude/skills/loca`) in step with CLI commands; `apps/cli/src/skills.test.ts` checks them.
