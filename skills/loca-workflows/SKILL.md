# loca 워크플로 만들고 돌리기

공통 규칙(연결, 제안, 권한)은 README를 따릅니다.

## 워크플로가 하는 일
번역 상태 사이에 놓인 자동화입니다. 진입 노드가 고른 상태의 대사를 받아 노드를 따라 흘려보내고, 대사마다 끝에 닿으면 마칩니다. 노드는 특정 게임이나 이름에 묶이지 않은 일반 노드입니다.

| 노드 | 하는 일 | 출구 |
|---|---|---|
| 진입(entry) | 고른 상태의 대사가 들어옴. 워크플로마다 하나 | `out` |
| AI(ai) | 모델·지시문·문맥으로 호출해 결과를 냄. 출력 종류: `text` 글 · `verdict` 판정 · `choice` 선택 · `json` 필드가 있는 JSON | verdict는 `pass`/`fail`/`error`, 나머지는 `out`/`error` |
| 반영(apply, 함수 노드의 한 갈래) | 프로젝트에 씀: 선으로 이어진 앞 단계(AI·스크립트 노드; 조건·다른 반영 노드는 건너뜀)의 결과를 번역·청자·태그·용어·인물·관계·말투 규칙·사건·문서로 넣고, 상태 변경·용어 상태 변경도 여기 속함(인물 저장은 설정 `profiles` 있음, 아래 참고) | `out`/`error` |
| 함수(function) | 읽고 판단·계산: 형식 검사, 용어 검사, HTTP, 스크립트. 모두 같은 입력(`unit`/`term`, `candidate` 지금 번역, `previous` 앞 단계 결과)을 받고 결과 칸을 돌려줌. 검사는 `{text, passed, issues, kind}` 고정(`kind`: 이 검사가 찾는 문제 유형 `format`/`term`; 검사는 통과·실패만 정하고 태그는 붙이지 않음), 스크립트·HTTP는 `fields`로 선언(HTTP는 `paths`로 응답의 위치). 결과의 `text`는 대사의 지금 번역이 됨 | 함수마다 다름 (reference) |
| 흐름: 조건(condition) | 대사의 데이터로 갈래를 나눔 | 조건식에 따라 |
| 흐름: 모으기(gather) | 실행 전체의 앞 단계 결과를 다 기다렸다가 하나로 넘김 | `out` |
| 흐름: 재요청(retry) | 실패한 대사를 AI 노드에 다시 보냄(작게·기다렸다가·다른 모델로). 설정 `{kinds (기본 ["cut-off"]; 오류 종류에 `rate-limit`(사용량 한도)·`network`(연결 끊김) 포함), scale (0.1–1, 기본 0.5; 1 = 그대로), wait (초, 0–3600, 기본 0 = 바로), model (null = AI 노드의 모델 그대로 | `{connectionId, model, effort?}` = 이 대사들만 그 모델로 같은 AI 노드에 보냄; 모델이 같은 대사끼리 묶음), maxTimes (1–5, 기본 2)}`. `kinds`에 든 오류이고 이 노드에서 `maxTimes`번 미만이면 `retry`(다시 보냄)로 나가 `wait`초 뒤에 AI 노드가 요청 크기에 `scale`을 거듭 곱해 보내고(기다리는 동안 실행은 계속되며 일시정지·취소·이어하기도 그대로), 아니면 원래 오류 그대로 `error`(오류)로 나감. 재요청의 `error`를 또 다른 재요청에 이어 사슬로 쓸 수 있음(앞 노드의 종류가 아니거나 횟수를 다 쓴 줄이 다음 노드로 가고, 노드마다 횟수를 따로 셈; 다시 보냄은 모두 같은 AI 노드로). 재요청은 AI 노드의 `error`(또는 다른 재요청의 `error`) 바로 뒤에만 둘 수 있음. AI 노드의 `error` → 재요청 → `retry` → 같은 AI 노드로 그림 | `retry`/`error` |
| 흐름: 워크플로 호출(call) | 같은 입력 타입의 다른 저장된 워크플로를 이 자리에서 돌림. 설정 `{workflowId}`. 끝까지 가면 `out`(완료), 실패로 끝나게 되면 `error`(오류, 오류 종류와 메시지를 가짐) | `out`/`error` |
| 종료(end) | 흐름을 마침 | — |

**워크플로 호출(`call`)**: 실행을 시작할 때 호출 노드가 부른 워크플로의 노드로 펼쳐집니다(그 순간의 내용으로 돌고, 도중에 그 워크플로를 고쳐도 이미 시작한 실행은 그대로). 부른 워크플로의 진입 노드와 `settings`는 쓰이지 않고 **부르는 쪽의 설정**(연속 실패·노드 방문 상한)이 적용됩니다. 부른 워크플로가 이 워크플로로 되돌아오는 순환은 저장할 때와 실행을 시작할 때 모두 거부됩니다(자기 자신, 여러 단계를 거친 경우 포함). 다른 워크플로가 부르고 있는 워크플로는 지울 수 없습니다(부르는 곳 이름이 오류로 나오니 호출을 먼저 지움). "앞 단계 결과"는 대사가 실제로 거쳐 온 노드의 결과입니다: 호출 안의 첫 노드는 호출 앞 노드의 결과를, 호출 뒤의 노드는 그 대사가 호출 안에서 마지막으로 거친 노드의 결과를 받습니다. 실행 기록에서는 안쪽 노드가 `호출 이름 › 노드 이름`으로 보이고 그래프에는 호출 하나가 카드 하나로 나옵니다.

**태그는 태그 붙이기(`tagLines`) 노드만 붙이고 뗍니다.** 형식 검사·용어 검사·AI 검수(verdict)는 판정만 하고 문제 유형 태그를 건드리지 않습니다. 설정 `{action: "add"|"remove", tagIds (프로젝트 태그), kinds (문제 유형 id: format·term·speech·meaning·style·other; 처음 붙일 때 프로젝트에 만들어짐), allKinds (remove 전용: 모든 문제 유형), map: {tag: 앞 단계 결과의 필드}}` — 고른 태그와 `map.tag`가 가리키는 값(AI 검수의 `categories`, 검사의 `kind`; 문제 유형 id·이름이나 태그 이름)을 함께 씁니다. 실패 출구 → 붙이기, 통과 출구 → 떼기(그 검사의 종류만; 검수가 통과하면 `allKinds`)로 잇습니다. 유일한 암묵 규칙은 번역 저장으로 대사의 번역문이 실제로 바뀌면 그 대사의 문제 유형 태그가 모두 떨어지는 것입니다(옛 번역에 대한 지적이라서). 기본 번역 워크플로가 이 배선을 보여 줍니다.

AI 노드는 결과를 **만들기만** 하고, 프로젝트에 넣는 건 반영 노드입니다. AI 노드의 프리셋은 여러 워크플로에서 쓰는 번역·검수 둘이고, 고르면 지시문·출력·문맥이 채워지며 고쳐 쓸 수 있습니다. 새 프로젝트의 기본 워크플로(번역, 청자 추정, 인물·관계 추출, 사건 추출)와 템플릿(용어 추출·번역, 작품 분석)의 지시문은 그 워크플로의 AI 노드 안에 있습니다(`loca workflows show`).

인물·관계 추출 워크플로는 `진입 → AI 인물·관계 추출(장면 묶음) → 모으기 → AI 인물·관계 합치기 → 인물 저장 → 관계 저장 → 말투 규칙 저장`입니다. AI는 새 인물뿐 아니라 이미 있는 인물에 대해 장면이 보여 주는 역할·성별·나이대·별칭·프로필도 냅니다. 장면을 읽는 동안에는 아무것도 저장하지 않습니다: 모으기가 모든 요청의 인물·관계·말투 규칙을 모으고(관계 변화·말투 시작·근거의 대사 id 포함), 합치기가 사람마다 하나, 쌍마다 하나(방향별 시각 하나 또는 둘 `views`, 각 시각의 변화 `changes`는 대본 순서이고 `{at, kind 바뀐 뒤의 관계, cause}`), 화자→청자 구간마다 하나로 합친 뒤(말투가 조각마다 다르면 관계와 근거의 다수로 정하고, 한 장면의 어조가 아니라 오래가는 변화일 때만 `startKey`를 둠) 각 목록을 한 번씩 저장합니다. 관계는 방향이 없거나 셋 이상이거나 한 방향이 겹치거나 쌍의 방향이 아니면 `invalid-output`으로 실패해 재요청 노드가 다시 보내고, 저장은 방향마다 행 하나(두 방향의 종류·변화가 같으면 쌍방 하나)입니다. 인물을 먼저 저장하므로 관계·말투 규칙이 이번에 새로 생긴 인물의 이름도 찾습니다(저장 노드는 결과를 그대로 넘기므로 세 저장 노드 모두 합치기 AI의 목록을 읽습니다). 인물 저장은 새 별칭을 더하되(다른 저장된 인물의 이름은 더하지 않음) 모르던 역할·성별·나이대를 채우고, 프로필·말버릇은 설정 `profiles`를 따릅니다: `fillEmpty`(기본)는 빈 것만 채우고, `propose`(이 템플릿의 인물 저장)는 빈 것을 채우고 AI가 쓰고 아무도 손대지 않은 것을 바꾸며 가져왔거나 사람이 쓴 것과 다르면 `save_character` 제안으로 올려 앱에서 수락하게 합니다(같은 제안이 대기 중이면 다시 올리지 않음).

## 입력: 대사 또는 용어
워크플로는 진입 노드의 `input`(`lines` 대사, 기본 / `terms` 용어집의 용어)으로 무엇이 들어오는지 선언합니다. 실행의 항목, 묶음, 범위, 개수가 그 단위가 됩니다. 노드는 코어 + 그 입력의 확장입니다. 입력마다 다른 것은 reference의 `inputs.table` 하나에만 있습니다(묶음 방식, 문맥 칸, 조건 행, 그 입력에만 있는 노드·프리셋).
- 진입 설정: `input` 하나뿐입니다. 어떤 대사·용어를 넣을지(상태, 표시, 장면, 고른 항목)는 실행 창·`loca runs plan/start`·`start_run`의 범위가 정합니다.
- 입력에만 있는 노드: 용어는 `saveTermEntry`(용어 표기 저장, `applyParams.onlyEmpty` 기본 true)·`setTermStatus`(용어 상태 변경), 대사는 형식·용어 검사·번역 저장·청자 저장·상태 변경·태그 붙이기. 다른 입력의 노드나 그 입력에 없는 묶음 방식(용어: 장면별·대본 전체)은 검증 오류입니다.
- AI 문맥: 대사는 앞 대사(번역)·이전 장면·청자·말투, 용어는 `examples`(0~5, 기본 2: 용어가 나온 대사를 번역과 함께).
- 조건: 대사는 `unit`(상태·종류·태그·자동 태그·청자), 용어는 `term`(`status`, `statusBy`, `hasTarget`, `lines` = 나온 대사 수, `marks`, `tagIds`).
- 전형적인 용어 입력 흐름: AI(`termTranslate` 프리셋: `target`, `note`) → `saveTermEntry`. `loca-glossary` 참고.

## 먼저 읽기
```
loca workflows list                       # 워크플로, 노드 수, 오류 수, 진입의 대상 상태
loca workflows show <워크플로> --json > "$W/wf.json"   # 정의 전체 {id,name,description,definition}와 검증 결과
loca workflows reference                  # 노드 종류·출구, AI 설정 스키마, 프리셋 요약, 함수·반영 대상, 조건 데이터, 규칙, 연결된 모델, 상태, 태그
loca workflows reference <프리셋 id>       # 그 프리셋의 지시문·출력 필드·문맥 전문 (예: listener)
```
만들거나 고치기 전에 reference를 꼭 읽습니다. 연결·모델·상태·태그 id는 여기 나온 것만 씁니다.

## 만들기·고치기
1. 비슷한 워크플로를 `show --json`으로 받아 고치는 게 가장 안전합니다. 새로 만들면 `id`를 빼고 `name`, `definition`만 씁니다.
2. `definition` = `nodes`(`id`, `type`, `position`, `label?`, `config`) + `edges`(`source`, `sourceHandle`=출구 id, `target`) + `settings`(`maxVisitsPerNode` 노드 방문 상한 기본 5, `maxConsecutiveFailures` 연속 실패 기본 3; 앱에서는 노드를 고르지 않았을 때 오른쪽 "워크플로 설정"에 보임).
3. 규칙 (reference의 `rules`가 기준):
   - 진입은 정확히 하나. `error`를 뺀 모든 출구를 잇습니다(이어지지 않은 `out`은 경고, 대사가 거기서 멈춤).
   - 화살표는 단계 순서입니다. AI 노드는 `concurrency`(동시 처리 수, 기본 1, 1–16)만큼 요청을 동시에 보내고, HTTP·스크립트 함수 노드는 자기 `config.concurrency`(기본 2, 1–8)만큼 호출을 동시에 보냅니다(`settings`에는 동시 처리 수가 없습니다). CLI 연결이면 그만큼 모델 프로세스가 뜹니다. 연결에는 동시 한도가 없고 실행마다 따로 셉니다. 다른 실행이 돌고 있으면 `loca runs plan`이 알려 줍니다. 실행 중 상황은 `loca runs show <id>` 또는 앱의 실행 기록 › 그래프에서 봅니다.
   - 병렬 갈래는 **한 출구에서 여러 간선**으로. 갈래끼리 다시 만나면 안 되고, 상태를 바꾸는 갈래는 하나까지.
   - 같은 출구에서 같은 노드로 간선 두 개 금지. 되돌아가는 고리에는 출구가 둘 이상인 노드가 있어야 합니다.
4. AI 노드:
   - `model`은 `{connectionId, model, effort?}`이고 AI 노드의 모델은 하나입니다(다른 모델을 쓰는 곳은 실패한 줄을 다시 보내는 재요청 노드의 `model`뿐이고, 연결에는 대체 모델도 자동 재시도도 없어 요청은 한 번에 한 경로로 한 번만 보냅니다).
   - `output: "json"`이면 `fields`로 형태를 정합니다: `name`(영문·숫자·_), `type`, `description`, 목록은 `fields`로 하위 필드, `required`(비면 그 줄은 답이 없는 것으로 침), 숫자는 `min`·`max`(예: 확신도 0–1). 모델이 지키지 못하거나 답에서 빠진 줄은 `error` 출구로 나갑니다(`error.kind` = `missing`).
   - `scope: "batch"`는 여러 줄을 한 번에 보냅니다(추출용). batch의 json 결과는 묶음의 첫 줄에만 실려 반영이 한 번만 됩니다.
   - `input`: `previous: true`면 선으로 이어진 **앞 단계의 결과**가 대사마다 `previous`로 들어갑니다. 앞 단계는 그 대사가 지나온 길에서 마지막으로 결과를 낸 노드이고(결과 칸을 선언한 노드: AI, 형식 검사·용어 검사 `{text, passed, issues}`, 스크립트, HTTP, 모으기), 조건·저장·상태 변경 노드는 건너뜁니다. 검사 뒤의 AI는 검사의 지적을 `previous`로 받고, 고칠 번역문은 문맥 `include.candidate`(지금 번역)로 받습니다(노드를 골라 먼 결과를 가져오지 않음, 필요하면 그래프를 그렇게 그림). `fields`로 경로만 남김(예: `["listener"]`, `["characters.name"]`; 비면 전체). 묶음 전체 결과는 묶음 첫 줄에만 있어 나머지 줄엔 들어가지 않습니다. `lines: false`면 대사 없이 `previous` 목록만 보냅니다(출력 `json` · `scope: "batch"`만).
   - `timeoutMinutes`(기본 10, 작품 분석 프리셋 30): 요청 하나가 이 시간을 넘으면 그 줄들은 `error`(`timeout`)로 나갑니다. 연결에는 제한 시간이 없습니다.
   - 실패는 워크플로가 다룹니다. 엔진은 요청을 나누거나 기다렸다 다시 보내거나 다른 연결로 넘기지 않습니다(요청 한도(`rate-limit`)·연결 끊김(`network`)도 다른 실패처럼 `error` 출구로 나가고, 출력 잘림을 포함해 실패한 요청이 `settings.maxConsecutiveFailures`번 연달아면 실행을 멈춤; 재요청 노드가 다시 보내는 실패는 세지 않음). 이어지지 않은 `error` 출구는 그 줄을 이유와 함께 실패로 끝내고, 실패한 줄은 앱의 실행 기록 › 이어서 실행의 "실패 다시 보내기"로 다시 돌립니다. 기본 템플릿의 모든 AI 노드는 같은 모양으로 실패를 다룹니다: `error` → 재요청 노드 A(출력 잘림·요청이 너무 김·답에서 빠짐·형식 오류·시간 초과를 절반 크기로 최대 2번 `다시 보냄`으로 되돌림) → A의 `오류` → 재요청 노드 B(사용량 한도·연결 끊김을 같은 크기로 60초 기다렸다가 최대 3번 되돌림) → B의 `오류`는 실패 표시로 이어집니다(번역·검수·수정은 상태 변경 `검토 필요로`, 용어 추출·인물·관계 추출·사건 추출·청자 추정은 태그 붙이기 `AI 실패 태그`; 용어 번역은 대사 태그를 용어에 붙일 수 없어 `오류`가 비어 있음). "다시 시도?" 같은 조건 노드는 쓰지 않습니다. 다르게 다루려면 재요청의 종류·크기·기다림·모델·횟수를 바꾸거나 `오류`를 다른 노드에 잇습니다. 사람이 볼 줄은 상태 변경·태그로 남깁니다.
   - 문맥(용어집·말투 규칙·앞 대사·노트·인물 등)은 노드마다 켜고 끕니다. 무엇이 실제로 들어가는지는 `loca context <키> -n <노드 id>`로 봅니다(모델은 부르지 않음).
   - 모으기(`gather`, 노드 종류 "모으기"): 앞 노드의 요청이 **모두** 끝날 때까지 기다렸다가 합친 결과 하나만 다음 노드로 넘깁니다(나머지 항목은 거기서 끝나고 경로에 `gathered`로 보임). 설정 `{fields}`: 모으는 결과는 선으로 이어진 앞 단계(AI·스크립트 노드)의 답이고, `fields`는 답마다 남길 경로(비면 전체). 결과는 `outputs.<모으기 id> = {parts: [앞 단계의 답마다 하나(묶음 답은 한 번), fields로 추림], count, failed(앞에서 실패한 항목 수)}`. 대사를 여러 요청으로 나눠 읽는 AI 노드 → 모으기 → 그 조각들을 합치는 AI 노드가 전형적인 모양입니다. 모으기 뒤에서는 항목을 바꾸는 노드(반영·상태 변경 등)가 거부되고, 모으기 바로 뒤의 AI 노드는 `input: {previous: true, lines: false}`로만 읽으며(`previous: [{parts, count, failed}]`로 들어옴), 고리 안에는 둘 수 없습니다.
5. 조건 노드는 JSON Logic입니다. 읽는 값: `visits`(노드별 방문 횟수), `outputs`(앞 노드 출력), `candidate`, `issues`, `unit`(`kind`, `speaker`, `listener`, `statusId`, `tagIds`, `marks`; 대사 입력, 용어 입력은 `term`), `error`(마지막으로 `error` 출구로 보낸 실패: `kind` = `missing`·`invalid-output`·`timeout`·`too-long`·`cut-off`·`rate-limit`·`network`·`refused`·`other`, `message`, `nodeId`; 조건을 지나도 남고, 작업 노드가 성공하면 지워짐). 예: `{"in": ["unknownListener", {"var": "unit.marks"}]}`, `{"<": [{"var": "visits.review"}, 3]}`, `{"==": [{"var": "error.kind"}, "missing"]}`. 노드 id와 상태 id는 reference·show에서 확인합니다.
6. 올리기:
   ```
   loca workflows save "$W/wf.json"         # id가 있으면 그 워크플로를 바꾸고, 없으면 새로 만드는 제안
   ```
   실행 중이거나 멈춘 실행이 있는 워크플로는 바꿀 수 없습니다. 수락 뒤 `loca workflows show <워크플로>`로 검증 결과(오류 0)를 확인합니다.

## 돌리기
AI 호출은 비용이 들어 시작도 제안이고, 사용자가 수락해야 시작합니다.
```
loca runs plan <워크플로> -g <장면>        # 읽기만: 대사 수, 묶음·요청 수 추정, 준비 상태
loca runs start <워크플로> -g <장면>       # 시작 제안. 범위와 옵션은 plan과 같음
```
- 범위(대사 입력): `-g` 장면·묶음, `--key` 대사, `--status` 상태(이름·id), `--mark` 표시, `--tag` 태그 (모두 만족). 아무것도 없으면 모든 대사입니다. 워크플로에는 대상 상태가 없습니다(범위는 실행할 때 정함).
- 범위(용어 입력): `--term <원문|id...>` 용어, `--status` 상태(후보·확정, 버림을 넣을 때만 명시; 용어집의 상태 열과 같음), `--mark` 용어 표시(`ai` AI가 정함, `emptyTarget` 번역어 없음, `unused` 대본 미등장), `--tag` 용어 태그. 아무것도 없으면 모든 용어(많이 쓰인 순). 대사 범위 옵션(`-g`·`--key`)은 용어 입력 워크플로에, `--term`은 대사 입력 워크플로에 쓸 수 없고 서버가 거절합니다. plan의 개수는 용어 수이고 청자·말투 규칙 준비 상태는 나오지 않습니다.
- `--model "연결:모델"`(모든 AI 단계) 또는 `--model "노드=연결:모델"`(한 단계)로 이번 실행만 다른 모델을 씁니다. 워크플로는 바뀌지 않습니다.
- plan의 **준비 상태**(청자 미상 대사, 확인 안 한 말투 규칙·용어, 규칙 없는 화자 쌍)에 걸린 것은 시작 전에 사용자에게 알립니다. 고치는 법은 `loca-knowledge`, `loca-glossary`.

## 실행 보기와 실패 원인
```
loca runs list --since 24                 # 최근 실행: 상태, 대사(용어 실행은 용어) 수, 토큰, 실패가 많은 노드
loca runs show <id>                       # 노드별 진행(상태별 대사·용어 수)과 최근 실패
```
실패가 한 노드에 몰리면 그 노드의 설정(모델, 출력 필드, 지시문)과 연결 상태를 봅니다. 모델이 출력 형식을 못 지키면 필드 설명을 구체적으로 쓰거나 `required`·`min`·`max`를 점검하고, 연결이 막히면(사용량 한도·연결 끊김) 오류 출구의 재요청 노드로 기다렸다 다시 보내거나 다른 모델로 보냅니다(AI 노드의 모델은 하나입니다).
